Your 4 schemas, their tables, and why

### 1. Database Schemas

I divided the BidNile database into four logical schemas based on their business responsibilities:

- **Core:** Contains City, Member, and Wallet. It manages member information, locations, and wallet balances
- **Operations:** Contains Warehouse and Employee. It manages warehouse information and employees
- **Catalog:** Contains Category, Item, and ItemPhoto. It organizes product listings, categories, and photos
- **Sales:** Initially contains Auction, Bid, and AuctionFollow. It manages auctions, bids, and auction followers

This separation improves database organization and makes the system easier to maintain and helps me give premissions to users according to schema 

In Task 3.12, I created the Marketing schema and transferred AuctionFollow from Sales to Marketing as required



### 2. Relationship Types

**1:1 — Member and Wallet**

Each member can have only one wallet
 I implemented this using a surrogate primary key in Wallet and a UNIQUE foreign key on MemberId referencing Member.Id

**1:N — City and Member**

One city can have many members, but each member belongs to one city
I implemented this using Member.CityId as a foreign key referencing City.Id
**M:N — Member and Auction**

Members can follow multiple auctions and auctions can have multiple followers
 I implemented this using the AuctionFollow junction table with MemberId and
  AuctionId as foreign keys and a composite UNIQUE constraint to prevent duplicate follows

**Recursive — Member Referrals and Category Hierarchy**

Member.ReferredByMemberId references Member.Id to represent referrals between members

Category.ParentCategoryId references Category.Id to represent parent and child categories

**Circular — Warehouse and Employee**

 Employee.WarehouseId references Warehouse.Id
 while Warehouse.ManagerId references Employee.EmpId
 These two foreign keys form a circular relationship

**Weak Entity — ItemPhoto**

ItemPhoto depends on Item for its identity
 I used a composite primary key consisting of ItemId and PhotoPosition
 ItemId is also a foreign key referencing Item.Id with ON DELETE CASCADE


### 3. Data Type Decisions

**Why GUID for Members?**

I used UNIQUEIDENTIFIER because member IDs can be generated by the mobile application before reaching the server
 GUIDs allow distributed ID generation with a very low risk of collisions
  The server uses NEWID() as a default when no ID is provided

**Why BIGINT for Bids?**

BidNile expects hundreds of millions of bids annually
 and the bid counter is expected to exceed 2.1 billion
  INT has a maximum value of 2,147,483,647
   so BIGINT provides enough capacity for future growth.

**Why FLOAT for GPS but DECIMAL for Money?**

GPS coordinates are approximate measurements with many decimal places
 so FLOAT is suitable
 - Financial values require exact decimal precision
  so I used DECIMAL(12,2) for balances and prices to avoid floating-point rounding errors

**Why DATETIMEOFFSET for Auctions?**

BidNile operates across different time zones including Cairo, Riyadh, and Dubai
 DATETIMEOFFSET stores the date, time, and UTC offset, allowing accurate comparisons between auction start and end times across these locations

### 5. Data Entry Order

I entered the data in an order that don't have foreign key dependencies 

1. **City:** Independent table.
2. **Member:** Requires existing cities and  Referring members were inserted before invited members
3. **Wallet:** Requires existing members
4. **Warehouse:** Requires existing cities
5. **Employee:** Requires existing members and warehouses
6. **Category:** Parent categories were inserted before child categories
7. **Item:** Requires existing sellers and categories, with optional warehouses and inspectors
8. **ItemPhoto:** Requires existing items
9. **Auction:** Requires existing items
10. **Bid:** Requires existing auctions and members
11. **AuctionFollow:** Requires existing auctions and members

**Circular Relationship Handling:**

I first inserted warehouses with NULL ManagerId, then inserted employees linked to those warehouses
 then I updated each warehouse with its manager's ID and management start date

This order avoids foreign key violations and allows all related records to be inserted successfully

To solve this I created both tables without foreign key constraints
 then added the foreign keys using ALTER TABLE after both tables existed

### 6. Errors in Tasks 3.6 and 3.11

**Task 3.6 — Changing MaxItems Data Type**

The ALTER COLUMN operation was blocked because MaxItems had a dependent CHECK constraint

I fixed this by dropping the CHECK constraint
changing MaxItems from INT to SMALLINT
 and recreating the constraint using WITH CHECK to validate existing rows

I also ensured that the values were within the valid range of 1 to 30,000

**Task 3.11 — Dropping IsVerified**

Dropping the IsVerified column was blocked because it had an attached DEFAULT constraint

I fixed this by adding VerifiedAt as a nullable DATETIME2(3) column, dropping DF_Member_IsVerified and then dropping the old IsVerified column

Both changes were performed using ALTER TABLE without dropping or recreating the tables
